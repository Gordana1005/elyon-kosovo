# Products, stock, warehouse & fulfilment

> The catalogue, how SKUs/barcodes work, where stock changes, the warehouse hand‑off, the **actual**
> Daily Fulfilment CSV format, and the courier‑office system.

## 1. Products catalogue

Table: `products` ([DATABASE.md](DATABASE.md) §3.2). **55 active items.** Admin page:
[../src/pages/ProductsPage.tsx](../src/pages/ProductsPage.tsx).

| Field | Meaning |
|---|---|
| `name` | Cyrillic product name (the catalogue key in many lookups) |
| `sku` | **Internal panel SKU** (e.g. `NT0095…`) — auto‑generated by the `set_product_sku` trigger if null |
| `barcode` | EAN barcode (partial‑unique) |
| `price` | **Website retail price = the agent's default selling price** (EUR). Shown to everyone. |
| `cost_price` | Wholesale cost (EUR). **Admin‑only** (gated by `financial_visibility.show_cost`). |
| `stock_quantity` | On‑hand units |
| `low_stock_threshold` | Low‑stock line (default 5) → `<StockBadge>` colour |
| `is_active` | Order modals only offer active products |
| `supplier_id` | FK → suppliers |

### SKU vs barcode — the settled rule (it flipped 3× before this)
`products.sku` = the **internal panel SKU** (`NT0095…`), **not** the EAN barcode. Four products keep
barcode‑as‑sku for historical reasons. The fulfilment CSV exports `sku:quantity`, and the BigArena import
matches on SKU then barcode then name. See `scripts/fix-skus-to-nt.mjs` (the final fix, 2026‑05‑22) and
the memory note `project_product_sku_decision`.

### Suggested selling price (server‑computed)
`GET /products` returns a suggested price = `max(cost_price × 3, current price, €15)`. The agent's default
is the **website retail price** when set; cost is never exposed to agents.

## 2. Stock model

**Stock changes only on `shipped` and `returned`** — never on order creation or confirmation. It lives in
two endpoints / four code blocks (see [BACKEND_API.md](BACKEND_API.md) §5):

```
confirmed ──(ship)──►  stock − quantity,  inventory_logs reason=order_deduction
shipped   ──(return)─►  stock + quantity,  inventory_logs reason=order_return
```

Rules:
- **Only fires when `order_items.product_id` is set.** The ~14k legacy import items are `product_id = null`
  and are intentionally skipped (they're history).
- **Multi‑product aware:** iterates `order_items`; falls back to the legacy single `orders.product_id`.
- **Availability check:** single `PATCH …/status → shipped` returns **400** if any item is short. The
  **bulk** flip (Fulfilment CSV) **skips** short orders (keeps them `confirmed`) rather than failing the batch.
- Every change writes an `inventory_logs` row (`previous_stock`, `new_stock`, `change_amount`, `reason`,
  `user_id`, `notes`). `reason` ∈ `order_deduction · order_return · bigarena_import · restock · manual · manual_adjust`.
- **Restock**: `POST /restock` adds stock + logs (supplier, invoice).

> **Don't deactivate** a product with open orders awaiting shipment — the order modal filters to `is_active`
> and the line would lose its catalogue link.

## 3. Inventory imports (BigArena)

**Stock sync from the UI (primary path).** Warehouse → **Inventory** → **BigArena Stock**
accepts the fulfilment‑panel export (CSV *or* XLSX) straight from BigArena and makes CRM stock
match the warehouse. Flow: parse client‑side → preview every diff → `POST /api/products/bigarena-stock-sync`.

- CRM `stock_quantity` = **"Свободна наличност" (free)** only. Reserved units are already
  committed to orders, so they are shown in the preview but never added in.
- Match order is **SKU → barcode → normalized name**, computed identically on the client
  (preview) and the server (apply) — the server re‑matches and never trusts a client id.
- Rows sharing a barcode are **merged by summing** free stock (e.g. `NT0108` + `000982`,
  barcode `5310416000743`) — same rule as the script.
- Products in the file but **not in the CRM are only reported**, never created. Add real new
  ones by hand from Products; most are legacy duplicate SKUs.
- Every change writes `inventory_logs` with `reason=bigarena_import`,
  `movement_type=bigarena_sync`, the operator's `user_id` and the file name in `notes`.
  Visible under Warehouse → Movements, filter "BigArena Sync".
- Idempotent: re‑uploading the same file reports 0 updated.
- Roles: admin, manager, warehouse. Rate limited to 5 uploads/min, max 500 rows/upload.
- Parser + matcher: [`src/lib/bigarenaStock.ts`](../src/lib/bigarenaStock.ts)
  (unit tests in `bigarenaStock.test.ts`); UI: `src/components/BigArenaStockSync.tsx`.

**CLI fallback.** `scripts/import-products-bigarena.mjs` (**idempotent**) pulls the BigArena fulfilment‑panel XLSX and
upserts products by SKU (then name fallback), merging duplicate barcodes by **summing** stock. Heuristic:
**stock > 10 inserts new; stock ≤ 10 updates only.** Every change → `inventory_logs reason=bigarena_import`.
`scripts/reconcile-panel-pdf.mjs` reconciles the catalogue against a fresh panel PDF. See [IMPORT_EXPORT.md](IMPORT_EXPORT.md).

**Order tracking / status reconciliation (separate daily flow):**  
BigArena also returns a tracking export (CSV or XLSX with "Ref: NNNN" + Статус). Upload it in the CRM (Orders or Warehouse UI) to automatically close the loop: `shipped` → `paid` on client acceptance / merchant payment confirmation, or `shipped` → `returned` on refusals. This reuses the exact same guarded bulk-status + stock + history paths as manual warehouse actions. See [ORDERS_AND_CLIENTS.md](ORDERS_AND_CLIENTS.md) for the state machine and the BigArena sync component.

## 4. The Daily Fulfilment CSV (warehouse hand‑off)

Generated **client‑side** in [../src/pages/Orders.tsx](../src/pages/Orders.tsx) (the "Daily Fulfilment CSV"
popover) using [../src/lib/csv.ts](../src/lib/csv.ts). This is the artefact the warehouse imports to ship.

> ⚠️ **Format note (supersedes CLAUDE.md / how‑it‑works.md):** the fulfilment CSV is **comma‑separated,
> NO BOM** — the call is `toCsv(eligible, [...], ',', false)`. The old docs say "semicolon + BOM, never
> change"; that was the *generic* `toCsv` default and an older warehouse spec. The **current** warehouse
> importer wants **comma + no BOM**. The generic `toCsv` default (`;` + BOM) is still used by other
> exports (e.g. product CSV). Don't "fix" the fulfilment export back to semicolon. (See [AUDIT_FINDINGS.md](AUDIT_FINDINGS.md).)

### Columns (in order)
`order_id` (digits of display_id) · `customer_name` · `customer_telephone` (BG national `0XXXXXXXXX`) ·
`products (sku:quantity)` (items joined by `;` inside the one cell, using panel SKU → product_name → `NA`) ·
`postal_code` · `country_code` (`BG`) · `city` · `address` · `order_date` (`yyyy-MM-dd H:mm:ss`) ·
`courier` (`speedy`/`econt`) · `courier_service` (`office`/`door`) · `payment_method` (`cod`) ·
`currency_code` (`BGN`) · `payment_amount` (**BGN/лв**, EUR×1.95583) · `note` (delivery_instructions) ·
`other` (gift_note) · `call_center` (`1`) · `amount_bgn` · `amount_eur`.

### Selection logic
- Filter to a status bucket (normally **confirmed**) and a date range.
- **"Ready to ship by" cutoff** (default today + 2): orders with `ship_after_date` **after** the cutoff are
  held back (postponed) and excluded; orders with no `ship_after_date` always pass.
- **Office vs home:** office orders put `office #<code> <name>` in `address`, the office city in `city`,
  and `courier` from `delivery_type`; home orders use granular address (`quarter, street, бл./ет./ап.`) and
  the agent‑chosen `home_courier` (defaults to econt).
- Phone is converted from stored `+359…` to BG national `0…`.

### "Mark as shipped after export"
A role‑gated checkbox (admin/manager/warehouse). When exporting the **confirmed** bucket with it on, after
the CSV downloads the eligible orders are bulk‑flipped **confirmed → shipped** (`POST /orders/bulk-status-update`),
which decrements stock and writes history. Postponed (held‑back) orders stay `confirmed`. Exporting any
other bucket is treated as a re‑export and does **not** move anything.

## 5. Warehouse page

[../src/pages/WarehousePage.tsx](../src/pages/WarehousePage.tsx) — a **calendar of scheduled shipments by
`ship_after_date`** plus the incoming‑orders feed (`GET /warehouse/incoming-orders`, filterable by agent/
date/product/source/status). Warehouse users can flip statuses (confirmed→shipped, →paid, →returned) within
their allowed set. `warehouse/user-items` (table `user_warehouse`) assigns specific product stock to a
warehouse user.

The warehouse itself is **outside the CRM** — it receives the Daily Fulfilment CSV (by email/upload) and
ships via Speedy/Econt. The CRM is the system of record; the warehouse software is BG‑locale Windows.

## 6. Couriers & offices (Speedy + Econt)

Table: `courier_offices` (~1888 active). Picker: [../src/components/DeliveryMethodPicker.tsx](../src/components/DeliveryMethodPicker.tsx)
(Home / Speedy / Econt pills → cascading City → Office autocomplete).

- **Cities:** `GET /courier-offices/cities?courier=&q=` — distinct cities matching a prefix on
  `city_normalized` (Latin), so `С`/`S`/`со`/`so` all match София.
- **Offices:** `GET /courier-offices?courier=&city=` — offices in a city (code, name, address, hours, lat/lng, **post_code**).
- **Free‑text match:** `GET /courier-offices/match?courier=&q=` — ranks offices for a legacy prose address
  ("офис на Еконт, кв. …") so old orders can be back‑filled with a real office code.
- **By code:** `GET /courier-offices/by-code` — render a saved selection.

**Office post codes:** an office order's `postal_code` is set to the **courier office's own post code**
(`resolveOfficePostCode`), so the CSV carries a valid code for offices just like home addresses. Don't
"fix" Sofia offices to `1000` — couriers route by office code; the office's own post code is correct
(memory note `project_office_postal_codes`).

**Refresh:** `scripts/scrape-courier-offices.mjs --commit` (idempotent) re‑enumerates Speedy via
`searchOffices.php` + `getOfficeDetails.php` and Econt via `Nomenclatures.getOffices.json`. Also exposed as
`POST /courier-offices/refresh` (admin/manager, rate‑limited).

**BG settlements** (`bg_settlements`, from `scripts/fetch-bg-settlements.mjs`) back the home‑address city
autocomplete; street/quarter suggestions are fetched live from Econt and cached per warm function instance.
